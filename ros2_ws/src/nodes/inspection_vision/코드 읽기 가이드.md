# Vision Node 코드 읽기 가이드

이 문서는 ROS, 카메라 SDK, 비동기 Queue를 처음 접하는 팀원이 코드를 한 번에
이해할 수 있도록 실행 흐름을 쉬운 순서로 설명합니다. 처음부터 `vision_node.py`의
모든 callback을 따라가지 말고 아래 순서로 읽는 편이 좋습니다.

## 1. 먼저 알아둘 세 가지 객체

### Frame

카메라 한 대가 한 번 찍은 이미지입니다. `CameraFrame`에는 RGB byte뿐 아니라
`nFrameNum`, 외부 trigger count, camera timestamp, host callback 도착 시각이 같이
들어갑니다. 이미지 내용만으로는 어떤 촬영 명령의 결과인지 알 수 없기 때문에 이
metadata가 꼭 필요합니다.

### FrameBatch

한 station 촬영 명령에 필요한 모든 카메라 Frame의 묶음입니다. Station A는 3장,
Station B는 1장입니다. `frame_batch_id`는 한 attempt의 저장 결과를 식별합니다.
첫 attempt의 skew가 실패하고 두 번째 attempt가 성공하면 `capture_id`는 같지만
`frame_batch_id`와 `attempt`는 다릅니다.

### InferenceJob

worker가 처리할 Queue 항목입니다. 이미지 byte나 raw file을 넣지 않고 RGB PNG의
절대경로만 넣습니다. 또한 `product_id`, `fifo_sequence`, `station_id`, `capture_id`,
`frame_batch_id`, `inference_job_id`를 함께 보존합니다.

## 2. 추천 읽기 순서

1. `capture_contract.py`
   - `CameraFrame.validate()`에서 한 프레임의 최소 조건을 봅니다.
   - `RawCaptureBatch.validate()`에서 필수 카메라 집합을 확인합니다.
   - `CaptureBatch.validate()`에서 저장 파일, SHA-256, RGB PNG를 확인합니다.
2. `artifact_store.py`
   - `encode_rgb8_png()`가 RGB byte를 canonical PNG로 만듭니다.
   - `ArtifactStore.save_batch()`가 날짜/제품/station/attempt 경로를 만듭니다.
   - `_atomic_write()`에서 temp, fsync, rename, readback 순서를 봅니다.
3. `capture_service.py`
   - `CaptureService.capture()`의 attempt loop가 전체 재촬영 정책입니다.
   - 첫 attempt 실패 뒤 `prepare_retry()`를 호출하고 고정 sleep은 하지 않습니다.
4. `inference_queue.py`
   - `InferenceQueue.try_enqueue()`가 `fifo_sequence` 기준으로 삽입합니다.
   - `get()`이 실제 worker가 꺼내는 순서입니다.
   - `WorkerPool`은 파일 읽기와 model 호출을 각각 1회 재시도합니다.
5. `queue_journal.py`
   - `prepare()`는 아직 Queue 등록 완료가 아닌 상태입니다.
   - `mark_enqueued()` 뒤의 pending/running만 process restart 때 복원합니다.
6. `vision_runtime.py`
   - 위의 순수 객체를 묶는 orchestration입니다.
   - 이 파일에는 ROS message나 `rclpy` import가 없습니다.
7. `vision_node.py`
   - 마지막으로 읽습니다. 순수 결과를 ROS Action/Message로 바꾸는 얇은 adapter입니다.
8. `mvs_backend.py`
   - 실장비 작업을 할 때만 자세히 읽습니다. SDK가 없는 test 환경에서는 import되지
     않으며 hardware initialize 시 lazy import됩니다.

## 3. Initialize가 두 단계인 이유

Master가 `InitializeNode`를 보내면 Vision은 먼저 다음 자원을 준비합니다.

- data directory와 disk policy
- SQLite queue journal
- sim 또는 MVS camera backend
- model artifact 검증과 warmup
- worker thread 객체

이 시점에는 아직 NodeBase가 새 `session_id`를 적용하지 않았습니다. worker가 즉시
돌아가면 이전 journal job의 결과가 빈 session 또는 이전 session으로 발행될 수
있습니다. 그래서 `VisionRuntime.start()`는 job을 복원하되 worker를 시작하지
않습니다. NodeBase가 session을 적용하고 health를 READY로 바꾸면
`VisionNode.set_health_state()`가 `activate_workers()`를 호출합니다.

같은 process에서 Initialize가 다시 오면 active capture가 없는지 먼저 확인하고,
이전 runtime을 닫은 뒤 journal에서 enqueue 완료 job만 복원합니다. 이전/새 worker가
같은 job을 동시에 처리하지 않게 하는 선택입니다.

## 4. Capture Action을 따라가는 방법

`VisionNode._execute_capture()`부터 시작합니다.

1. Node health, session, command epoch, UUID, SHA 형식을 검사합니다.
2. Master와 같은 payload 필드로 digest를 다시 계산합니다.
3. 같은 command ID가 같은 digest로 재전송되면 이전 결과를 재사용합니다.
4. station camera 배열의 값뿐 아니라 순서까지 config와 같은지 검사합니다.
5. station lock과 각 camera lock을 잡습니다.
6. `CaptureService.capture()`를 부릅니다.
7. 저장된 batch를 `VisionRuntime.enqueue_saved_batch()`에 넘깁니다.
8. journal commit과 Queue insert가 모두 끝나면 Action success를 반환합니다.

Action feedback 숫자는 ROS interface에 정의되어 있고, 순수 계층에서는 읽기 쉬운
`CaptureProgressStage` 문자열을 사용합니다. `_publish_domain_progress()`가 둘 사이를
변환합니다.

## 5. 카메라 프레임과 촬영 요청이 연결되는 방법

카메라 stream에는 오래된 프레임이나 늦게 도착한 이전 attempt 프레임이 섞일 수
있습니다. 단순히 “callback에서 다음으로 온 한 장”을 쓰면 잘못된 제품을 연결할 수
있습니다. MVS backend는 Action Command 직전에 다음을 수행합니다.

1. `MV_CC_ClearImageBuffer()`로 SDK 대기 buffer를 비웁니다.
2. 카메라별 마지막 `nFrameNum`과 `nTriggerIndex`를 baseline으로 저장합니다.
3. host `trigger_requested_monotonic_ns`를 기록합니다.
4. active attempt window를 callback과 공유합니다.
5. immediate `MV_GIGE_IssueActionCommand()`를 보냅니다.

callback은 함수에 들어온 즉시 host monotonic/wall 시각을 찍고 source buffer를
복사합니다. 다음 조건을 만족하는 후보만 이번 attempt에 넣습니다.

- callback 도착이 trigger 요청 이후
- 외부 trigger count가 제공되면 baseline보다 뒤의 count
- 그렇지 않으면 `nFrameNum`이 baseline보다 뒤의 값

counter 비교는 uint32 wrap-around도 처리합니다. filename의 문자열 timestamp는
상관관계에 사용하지 않습니다.

## 6. timestamp 필드의 차이

- `trigger_requested_monotonic_ns`: host가 Action SDK 함수를 부르기 직전 시각
- `trigger_returned_monotonic_ns`: Action SDK 함수가 반환된 직후 시각
- `host_arrival_monotonic_ns`: camera callback에 진입한 host 시각; timeout/skew 계산용
- `host_arrival_wall_time_ns`: 사람이 읽는 UTC 로그/파일 날짜 연결용
- `camera_timestamp_raw`: MVS high/low 32-bit 값을 합친 원본 device tick
- `camera_timestamp_ns`: tick 주파수가 확정된 경우에만 변환한 값
- `camera_timestamp_synchronized`: PTP 지원 확인만으로 true가 되지 않으며 안정적인
  lock을 실측한 뒤에만 true여야 함
- `sdk_host_timestamp_raw`: MVS가 FrameInfo에 넣은 `nHostTimeStamp` 원본

현재 공식 skew는 모든 `host_arrival_monotonic_ns`의 max-min입니다. PTP camera
timestamp skew는 향후 검증을 위한 로그 자료이지 현재 합격 판정값이 아닙니다.

## 7. 저장이 성공했다는 의미

`ArtifactStore._atomic_write()`는 다음 순서를 모두 통과해야 성공입니다.

1. 충돌하는 같은 경로가 없는지 확인
2. `.vision-tmp` 파일을 exclusive create
3. 전체 byte write
4. file flush + `fsync`
5. Linux 권한 0660 적용
6. `os.replace()`로 최종 이름 노출
7. parent directory `fsync`
8. 최종 size와 SHA-256 readback
9. `CaptureBatch.validate()`의 PNG CRC/IHDR/압축 stream 검사

같은 내용의 파일이 이미 있으면 멱등 재사용할 수 있지만, 같은 경로에 다른 내용이
있으면 덮어쓰지 않고 오류로 처리합니다. 재시작 시 `.vision-tmp`만 지우며 완료된
실패 attempt는 원인 분석을 위해 남깁니다.

## 8. Queue full일 때 Action이 끝나지 않는 이유

Queue가 가득 차면 이미 제품은 station에서 촬영되었고 파일 저장도 끝났습니다.
Action을 실패시키고 새로 촬영하면 실제 제품 위치와 image identity가 섞일 수
있습니다. 따라서 다음 순서를 사용합니다.

1. journal에는 pending, `enqueue_committed=0`으로 기록
2. `ENQUEUE_BLOCKED` feedback과 Queue state 발행
3. Master가 PAUSED 전이를 수행
4. Queue depth가 capacity의 50% 이하가 될 때까지 동일 Action 대기
5. 같은 job을 Queue에 삽입
6. Queue 내부 lock을 잡은 채 journal을 `enqueue_committed=1`로 변경
7. `ACCEPTING` 상태와 Capture success 반환

process가 4번 이전에 죽으면 enqueue 미완료이므로 journal 복원 대상이 아닙니다.
5~6번의 critical section 뒤에 죽으면 enqueue 완료 상태이므로 재시작 후 복원됩니다.

## 9. worker와 model lock

worker는 Queue에서 job을 꺼내면 journal을 running으로 바꿉니다. worker 2개는 PNG
파일 읽기를 병렬로 할 수 있지만, 기본 설정에서는 하나의 model lock을 공유해 GPU
inference를 직렬화합니다. 실제 model의 thread safety와 CUDA stream 시험이 끝나기
전 안전한 기본값입니다.

완료 순서는 FIFO일 필요가 없습니다. FIFO는 “꺼내는 순서”까지이고, worker 실행
시간이 달라 Station B가 A보다 먼저 완료될 수 있습니다. Master는 ID와 revision으로
결과를 연결합니다.

## 10. 실패를 읽는 기준

- 촬영/파일 저장/Queue enqueue 전 실패: Capture Action 실패
- enqueue 이후 file read/model/timeout 실패: `StationInferenceFailed`
- score NaN/Inf 또는 잘못된 verdict: inference 실패
- `ProductResultLocked` 뒤: late 성공 발행 안 함, job `locked`
- 카메라 복구 3회 실패: Vision `INIT_BLOCKED`, 모든 station 차단
- 정상 cancel 또는 product locked: camera station 장애로 오인하지 않음

각 job은 성공과 실패 중 하나만 Master에 보내야 합니다. 결과 publish가 끝난 다음
journal을 done으로 바꿉니다. publish 전에 process가 죽으면 running job이 복원되어
같은 revision으로 재처리될 수 있으므로 Master의 멱등 revision 검사가 필요합니다.

## 11. 실제 추론 코드를 넣을 위치

기존 파일에 PyTorch 코드를 직접 섞지 않습니다. 별도 Python package에 factory를
만들고 `vision.model.factory`로 지정합니다. factory는 model path와 device를 받아
adapter를 반환합니다. `infer(images_rgb)` 입력 배열은 station config의 camera ID
순서와 같습니다.

추론 담당자는 다음을 반드시 자기 package README에 기록해야 합니다.

- artifact version과 SHA-256
- PyTorch/CUDA/cuDNN 버전
- 입력 resize/crop/normalize와 dtype
- 카메라별 ROI와 순서
- score의 수학적 의미와 유효 범위
- PASS/NG threshold와 불확실 구간
- Station A 3 camera 결과 결합식
- warmup 입력과 기대 시간
- retry가 안전한 이유

## 12. 디버깅할 때 먼저 볼 것

- Initialize 실패: `GetNodeStatus.status_json`과 `VISION_INITIALIZATION_FAILED`
- camera 누락: serial/IP/MAC/model/firmware config와 MVS enumeration
- 잘못된 이미지: manifest의 frame/trigger counter와 모든 timestamp
- 잦은 skew 실패: host NIC/packet 설정과 callback 분포
- Queue PAUSED 반복: queue depth, worker latency, GPU utilization
- 재시작 뒤 누락: journal `enqueue_committed`, status, image path 존재 여부
- Log 누락: Vision spool DB와 `LogPersistedAck` producer instance/session

기록 항목을 먼저 확인하십시오.
