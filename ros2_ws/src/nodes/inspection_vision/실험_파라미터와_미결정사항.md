# Vision 실험 파라미터와 미결정사항

이 문서는 production 투입 전에 반드시 채워야 하는 값과, 운전은 가능하지만 시험으로
최적화할 값을 분리합니다. 빈 값과 0은 “자동 기본값”이 아니라 `hardware` 초기화를
막는 의도적인 표식입니다. 결정할 때는 값만 적지 말고 시험 조건·표본 수·분포·선택
근거·승인자를 같은 문서 또는 링크로 남깁니다.

## A. 현재 확정되어 코드에 고정된 항목

| 항목 | 값/정책 |
|---|---|
| Trigger 방식 | immediate `GIGE_ACTION_COMMAND`, scheduled=false |
| Trigger 구성 | FrameBurstStart, burst 1, TriggerMode On, TriggerSource Action1 |
| Action key | Device `0x13572468`, A Group 1, B Group 2, Mask `0xFFFFFFFF` |
| Camera topology | Station A 3대, Station B 1대 |
| Camera 종류 | MV-CS050-10GC, firmware 문자열에 `4.0.43` 포함 필수 |
| Pixel pipeline | BayerRG8 → MVS RGB8 packed → RGB PNG, OpenCV BGR→RGB |
| 해상도 | 2448×2048 |
| PNG | compression 3, RGB8, atomic write/readback/SHA |
| SDK buffer | camera별 8, OneByOne, retry 전 clear |
| 촬영 retry | 최대 2 attempts, 같은 capture ID, station 필수 카메라 전체 |
| skew 공식 | host callback arrival monotonic max-min |
| Queue 순서 | `fifo_sequence`, get 순서까지 FIFO |
| Queue 초기값 | capacity 16, warning 75%, resume 50% |
| worker 초기값 | 2 threads, model 1개 공유, model lock=true |
| retry | file read 1회, inference 1회 |
| restart | enqueue commit된 pending/running만 복원, 저장-only batch 재촬영 금지 |
| disk 초기 경계 | used 80/90/95%, free 20/10/5 GiB |
| reconnect | 최대 3회, delay 0/0.5/1.0초, 시험 촬영 3회 |
| 파일 권한 | directory 2770, file 0660, umask 0007 |
| LED | 코드/설정/인터페이스 없음 |

이 값 중 “초기값”은 아래 성능 실험 결과에 따라 정상 Git 변경 절차로 바꿀 수 있지만,
현재 코드와 YAML이 서로 다르면 안 됩니다.

## B. hardware READY 전에 반드시 확정할 값

### B-1. 카메라 identity와 Linux SDK

| 결정할 것 | 지금 상태 | 정확히 제공할 정보/인수 조건 |
|---|---|---|
| CAM_A_1 | 일부 확정 | serial `DA9880516`, IP `192.168.10.11`, MAC `34:BD:20:8A:22:8A` 실물 라벨·MVS enum 교차확인 |
| CAM_A_2 | 미정 | serial, MAC, 실제 IP `192.168.10.12` 일치 결과 |
| CAM_A_3 | 미정 | serial, MAC, 실제 IP `192.168.10.13` 일치 결과 |
| CAM_B_1 | 미정 | serial, MAC, 실제 IP `192.168.10.14` 일치 결과 |
| Linux MVS | 미검증 | Ubuntu 24.04용 정확한 5.0.2 package 이름/다운로드 출처, install checksum, shared library 경로 |
| Python wrapper | 미정 | `MvCameraControl_class.py`가 있는 절대경로와 Python 3.12 import 성공 로그 |
| SDK version | 목표 5.0.2/raw 미정 | `MV_CC_GetSDKVersion()` 실제 hex와 vendor version 대응표; 확인한 정수를 `vision.mvs.expected_sdk_version_raw`에 입력 |
| firmware | 목표 4.0.43 | 네 대 모두 enum의 `chDeviceVersion`에 기대 문자열 포함 |
| NIC | IP만 확정 | Linux interface 이름, `192.168.10.10/24`, route, camera 전용 여부 |

현재 `hardware.yaml`은 미확정 serial/MAC과 wrapper 경로를 빈 값으로, SDK raw version을
0으로 유지합니다. raw version이 0이면 hardware profile은 READY가 되지 않습니다.

### B-2. timestamp/PTP와 skew

| 결정할 것 | 왜 필요한가 | 정확히 측정/기록할 것 |
|---|---|---|
| device timestamp tick Hz | raw를 ns로 바꾸기 위해 필요 | vendor 문서값과 장시간 delta 측정값, wrap 주기 |
| timestamp domain | 다른 clock과 비교 가능 여부 | free-running/PTP domain 이름, reboot/reset 시 원점 변화 |
| PTP 실제 지원 | `synchronized` 판단 | 네 camera의 GevIEEE1588 writable 여부와 status enum |
| PTP lock 안정시간 | 일시 lock을 안정으로 오인 방지 | startup/reconnect별 lock 도달 분포, unlock flap, 허용 안정 유지 ms |
| synchronized 판정식 | 로그 신뢰도 | 어떤 status가 몇 ms 지속될 때 true인지, unlock 즉시 false 여부 |
| host skew limit | 촬영 합격/재촬영 결정 | 최소 수천 batch의 A 3-camera skew p50/p95/p99/max, 부하/온도/네트워크 조건 |
| camera timestamp skew | 향후 보조 진단 | PTP stable 구간의 max-min 분포; 현재 공식 합격값으로 사용하지 않음 |
| callback 기록 지점 | 구현 검증 | Python callback 첫 실행문 앞뒤 계측 overhead와 GIL 지연 |

`vision.camera.timestamp_tick_hz`, `vision.camera.ptp_stability_ms`,
`vision.frame_arrival_skew_limit_us`를 결과로 채웁니다. PTP 미지원 또는 안정판정 미정
상태여도 immediate Action과 host skew는 사용할 수 있지만
`camera_timestamp_synchronized=false`를 유지합니다. PTP 값 0 자체는 hardware capture를
막지 않으며, 동기화되었다고 주장하는 것만 금지합니다.

### B-3. model과 판정 알고리즘

| 결정할 것 | 정확히 필요한 정보 |
|---|---|
| artifact | 절대경로, semantic version, SHA-256, 학습 데이터/commit/model card 링크 |
| factory | `package.module:factory` 경로와 package 배포 방식 |
| runtime | PyTorch, CUDA, cuDNN, GPU driver의 고정 버전과 호환 표 |
| device | RTX 5070 Laptop GPU에서 사용할 `cuda:N`, VRAM 예산과 OOM 정책 |
| input | camera별 ROI, resize/crop, channel order RGB, dtype, range, normalize mean/std |
| camera order | A1/A2/A3 결합 순서와 B1 입력 계약; YAML 배열과 정확히 같아야 함 |
| batch | station 단위 tensor shape와 dynamic/static shape 여부 |
| 수학식 | camera별 score와 station score 계산식, A 3-camera 결합 규칙 |
| score | 의미, 정상 범위, calibration 방식; NaN/Inf 처리 |
| threshold | PASS/NG 경계, 불확실 구간과 안전측 우선 규칙 |
| output | `StationInference(verdict, score, model_version)` 매핑 |
| warmup | 입력 shape, 반복 횟수, 성공 기준, 최대 허용시간 |
| deterministic | seed/algorithm 설정, 같은 입력 재현 오차 범위 |
| retry 안전성 | 같은 입력 1회 재실행이 side effect/상태를 오염시키지 않는 근거 |
| 오류 | OOM, CUDA reset, invalid input, model exception별 recovery/노드 재초기화 정책 |

이 항목이 없으면 `vision.model.path`, `vision.model.sha256`,
`vision.model.factory`를 채우지 않습니다. sim model은 이 결정을 대신하지 않습니다.

### B-4. timeout과 용량

| parameter | 초기/현재 | 확정 방법 |
|---|---:|---|
| `vision.camera.frame_timeout_ms` | 2000 | exposure+network+callback 최악시간 p99.9에 안전 margin; Master capture timeout보다 작아야 함 |
| Action ACK timeout | 200 ms | packet loss/네 camera ACK 분포와 retry 영향 |
| `vision.inference_queue_total_timeout_ms` | 0(미정) | enqueue→완료 p99.9, Sensor3 이동시간보다 짧게 설정 |
| Queue capacity | 16 | 최대 유입 burst, 평균/최악 infer latency, 메모리/디스크/정지시간 |
| worker count | 2 | 1/2/3/4 worker throughput와 GPU utilization/VRAM/열 throttling 비교 |
| model lock | true | adapter thread safety와 multi-stream 정확도/성능 시험 전 해제 금지 |
| Master capture timeout | 30000 | 2 attempts+PNG fsync+Queue block 정책과의 관계; Queue block 중 갱신 동작 확인 |

Queue timeout은 Sensor3 이벤트에서만 시작하는 deadline과 다릅니다. 두 값을 같은
parameter로 합치지 않습니다.

### B-5. filesystem, 권한, 보존

| 결정할 것 | 정확히 필요한 정보 |
|---|---|
| data filesystem | mount device, filesystem 종류, 절대 root, 예상 write IOPS/fsync latency |
| service accounts | Linux `vision`, `log` 사용자 생성 방식과 공통 `inspection` group |
| permission | systemd `UMask=0007`, setgid directory 2770, file 0660 실제 시험 |
| disk threshold | 공정 정지 여유시간을 반영한 used%/free GiB 값과 둘 중 더 보수적인 조건 |
| PASS 보존 | 기간/표본 추출 비율/삭제 승인 |
| NG 보존 | 기간, 품질 분석/감사 요구 |
| failed/late 보존 | attempt, incomplete, recovery-test별 기간 |
| 삭제 handshake | LogNode가 어떤 event/revision으로 Vision 소유 파일 삭제를 요청·확인할지 |
| spool quota | Vision log spool, queue journal의 최대 크기와 장애 전 경고/정지 |
| DB backup | journal/spool backup 필요 여부, WAL checkpoint, 복구 시험 |

Vision은 완료 파일을 임의로 retention 삭제하지 않습니다. LogNode와 소유권 handshake가
확정되기 전에는 경로만 기록하고 보존합니다.

## C. 실험으로 최적화할 수 있는 항목

### C-1. 카메라 화질

- exposure time: conveyor 정지 뒤 진동/모션 blur와 밝기 분포를 함께 측정
- gain: noise, defect recall, 밝기 균일도
- white balance R/G/B: 외부 LED controller의 색온도와 lot 변화
- gamma: model 학습 pipeline과 동일 여부; 카메라/SDK/전처리 중 한 곳에서만 적용
- MVS Bayer conversion quality 0/1/2: 처리시간, edge artifact, model metric 비교
- packet size(MTU/jumbo), `GevSCPD`, bandwidth reserve: packet loss와 camera 간 skew
- exposure 시작/종료와 Action callback latency 분해
- station별 camera angle/focus/aperture/working distance 고정 및 변경 검출

각 변경은 canonical RGB 결과가 학습 pipeline과 같은지 golden image SHA/metric으로
검증합니다. 실험값을 바꾸어도 LED ON/OFF/밝기 제어 코드는 추가하지 않습니다.

### C-2. worker/GPU

- file load thread 병렬성과 NVMe read latency
- pinned memory, non-blocking H2D, mixed precision 사용 여부
- 공유 model lock 유지 vs model instance 복제
- CUDA stream 1개 vs worker별 stream
- worker CPU affinity/priority
- warmup 횟수와 first-product latency
- OOM 후 process 재시작 vs model reload
- PyTorch compile/TensorRT 등 최적화 전후 정확도 동등성

성능 향상은 PASS/NG 결과의 bitwise 또는 허용 오차 동등성, timeout 감소, GPU 온도와
장시간 안정성을 모두 만족해야 승인합니다.

### C-3. Queue와 운전 정책

- warning 75%와 resume 50%가 실제 유입 burst에서 잦은 pause oscillation을 막는지
- capacity 16에서 예상 정지 후 남은 제품 수를 흡수할 수 있는지
- Station A/B job 처리시간 차이가 starvation을 만들지 않는지
- `fifo_sequence`가 같은 A/B의 tie order(`enqueue time`, `station_id`)가 운영에 적합한지
- Queue total timeout sweeper 50 ms가 CPU overhead와 deadline 정밀도를 만족하는지
- full 상태에서 Master PAUSING/PAUSED/ACCEPTING 전이와 capture deadline 갱신 검증

FIFO는 worker가 꺼내는 순서까지입니다. 결과 완료 순서를 억지로 직렬화하지 않습니다.

### C-4. 파일/로그

- PNG compression 0~9의 CPU 시간, 크기, fsync latency; 현재 3
- 날짜 경계를 UTC로 사용하는 현재 구현과 현장 운영일 기준의 일치 여부
- directory 하나당 파일 수와 metadata lookup 성능
- LogEvent resend batch/period(현재 100개/1초)
- capture telemetry payload 크기와 DDS/SQLite 부하
- SHA-256 readback 비용과 production cycle time

## D. 장애/복구 acceptance에서 결정할 세부 기준

| 시험 | 합격 기준을 추가로 정할 것 |
|---|---|
| camera cable 분리 | 감지시간, 3 reconnect 총시간, all-station block 시점 |
| camera power cycle | IP/serial 재발견, config 재적용, callback 중복 등록 없음 |
| Action ACK loss | 실제 frame 수신과 ACK 실패가 다를 때 성공/실패 판단 정책 |
| late frame | 다음 attempt에 연결되지 않음, metadata/log 보존 여부 |
| partial frame | temp 삭제, 완료되지 않은 PNG가 canonical 이름으로 보이지 않음 |
| disk 80/90/95% | warning/PAUSED/critical의 Master 운전 반응과 복구 hysteresis |
| Vision kill before enqueue | uncommitted journal 실패, 자동 재촬영/복원 없음 |
| Vision kill after enqueue | pending/running 복원, duplicate result revision 안전 |
| kill during inference | model retry/재시작 후 same job 결과 멱등성 |
| ProductResultLocked race | queued 제거, running late success 미발행 |
| LogNode down | Vision spool 증가, 재연결 ACK 뒤 정확히 삭제 |
| corrupt PNG | read 1 retry 후 `INFERENCE_FILE_READ_FAILED` |
| NaN/Inf score | StationResult 미발행, StationInferenceFailed 발행 |

Action ACK가 실패했지만 프레임이 도착한 경우 등 애매한 물리 상태는 실장비 시험 전에
정책을 임의로 추정하지 않습니다. 현재 adapter는 SDK Action 호출/ACK 오류를 attempt
실패로 처리합니다.

## E. 현재 미검증 항목

- Ubuntu 24.04에서 MVS 5.0.2 native library와 Python 3.12 wrapper import
- 네 대 실제 camera simultaneous Action1 지원과 group filtering
- MVS callback 구조체/`nTriggerIndex`가 해당 firmware에서 실제로 증가하는지
- `MV_CC_SetBayerCvtQuality(1)`과 BayerRG8→RGB8 packed 출력 channel golden test
- PTP 지원·status·timestamp tick 단위
- NIC jumbo/packet 설정과 네 camera 최대 payload packet loss
- RTX 5070 Laptop용 CUDA/PyTorch 설치 및 실제 model warmup
- ROS 2 Jazzy `colcon build`, launch, Master–Vision live Action integration
- systemd user/group/permission과 `/var/lib/inspection` mount
- 8시간 이상 soak, cable/power/disk/process kill fault injection

검증 결과는 명령, 날짜, OS/kernel/ROS/SDK/firmware/GPU driver 버전과 함께 이 표를
갱신해야 합니다. “명령이 한 번 성공함”은 production acceptance가 아닙니다.
