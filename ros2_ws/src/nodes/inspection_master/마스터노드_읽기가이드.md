# MasterNode 코드 읽기 가이드

## 먼저 알아둘 점

완성 후에는 처음부터 모든 코드를 정독하실 필요가 없습니다. `master_node.py`는
하나의 큰 알고리즘이라기보다 여러 ROS callback과 복구 경로를 한곳에서
연결하는 조율 파일이므로, 전체 흐름을 먼저 보고 필요한 블록만 확대해서
읽는 편이 좋습니다.

## 1. 전체 공정 읽기 지도

### 프로그램 시작

```text
main()
└─ MasterNode.__init__()
   ├─ 설정·FIFO·작업 상태 생성
   ├─ Topic / Service / Action Client 연결
   └─ watchdog·log flush timer 시작

request_initialize()
↑ /inspection/master/operator_command (INITIALIZE)
└─ Block 1 FSM: BOOT → INITIALIZING
   └─ Block 2: Control·Vision·Log Initialize Action
      └─ Action Result + GetNodeStatus + heartbeat 교차 확인
         └─ READY
```

### 정상 제품 한 개

```text
request_run()
└─ Control에 RESUME 명령
   └─ confirm_all_conveyors_running()
      └─ RUN_SYS

_handle_sensor_event()
└─ Sensor1: _handle_sensor1_entry()
   ├─ product_id / fifo_sequence 발급
   ├─ ProductLedger의 단일 활성 FIFO에 등록
   └─ _start_station_cycle(A)
      ├─ _send_position_goal()
      ├─ PositionProduct Result + PositionSettled 모두 확인
      ├─ _request_station_capture(A)
      └─ _resume_conveyor_after_capture()
         └─ FLIPPING

Sensor2: _handle_sensor2_entry()
└─ FIFO의 가장 오래된 FLIPPING 제품을 선택
   └─ _start_station_cycle(B)
      └─ 위치 이동 → 촬영 → 재가동
         └─ SENSOR3_WAIT

_handle_station_result() / _handle_station_failure()
└─ A/B 추론 결과를 해당 ProductContext에 비동기 반영
   └─ 이 시점에는 최종 판정을 잠그지 않음

Sensor3: _handle_sensor3_entry()
├─ ProductContext.lock_at_sensor3()
│  └─ PASS / NG / FORCED_NG를 한 번만 잠금
├─ _accept_locked(): 판정 Topic + 로그
└─ _schedule_actuation()
   └─ _send_actuation_goal()
      └─ _handle_actuation_result()
         └─ _remove_completed_fifo_prefix()
```

핵심은 `촬영 완료 != 추론 완료`입니다. 촬영 후 컨베이어는 바로 재가동하고,
추론은 별도로 진행됩니다. Sensor3에 도착한 순간에만 최종 판정을
잠금합니다.
`StationResult.score`가 `NaN`·`Inf`처럼 유한하지 않으면 판정 근거로 사용하지
않고 비전 결과 계약 실패로 기록하여 Sensor3에서 `FORCED_NG`로 잠급니다.

### PAUSE·FAULT·RESET·종료

```text
복구 가능 장치 문제
└─ request_recoverable_device_pause()
   └─ PAUSING → 실제 정지 확인 → PAUSED
      └─ request_resume() → 가동 확인 → RUN_SYS

FIFO·product_id·물리 위치 붕괴
└─ _fault_stop()
   └─ FAULT_STOP + LINE_CLEAR_REQUIRED
      └─ confirm_line_cleared()
         └─ request_reset() → confirm_reset_completed() → READY

Ctrl+C
└─ request_shutdown()
   └─ 양쪽 컨베이어 실제 정지 확인
      └─ 진행 Action cancel + 로그 spool 보존 → 종료
```

LINE_CLEAR·제자리 복구와 종료에서 수행하는 Action cancel은 best-effort입니다.
실제 안전 정지는 RESET·PAUSE 명령과 Control adapter의 안전 출력이 보장해야 하며,
Control의 장시간 작업은 cancel 요청과 `command_epoch` 변경을 계속 확인해야 합니다.

`_handle_operator_command()`은 위 공개 함수를 터미널/HMI Service에 연결하는
진입점입니다. Service가 직접 컨베이어를 건드리지 않고 반드시
`request_run()` 등의 guard를 거칩니다.

## 2. 새로 만든 파일과 역할

### `inspection_master/system_fsm.py`

ROS와 무관하게 `현재 SystemState + SystemEvent → 다음 SystemState`를 결정합니다.
`_TRANSITIONS`는 설계 전이표를 코드로 옮긴 딱 하나의 표입니다.

### `inspection_master/worker_supervision.py`

Master가 보는 Control·Vision·Log의 초기화 상태입니다. Initialize Action의
응답만 믿지 않고 GetNodeStatus와 최신 heartbeat까지 교차 검증한 뒤 `READY`로
표시합니다.

### `inspection_master/product_flow.py`

제품 한 개의 `ProductContext`, Station A/B 상태, Sensor event, 최종 판정,
액추에이터 완료 여부를 보관합니다. `ProductLedger`가 모든 활성 제품을
단일 FIFO로 소유합니다.

### `inspection_master/operation_runtime.py`

ROS Action의 진행 중 상태를 보관합니다. `StationCycle`은 위치·촬영,
`ActuationCycle`은 분류 작업, `EquipmentSnapshot`은 컨베이어·센서·액추에이터
실제 상태를 Master가 보는 mirror입니다.

### `inspection_master/master_node.py`

위 순수 상태 객체와 ROS Topic·Service·Action을 연결합니다. 파일 안에
`# region BLOCK 1`부터 `BLOCK 8`까지 구역이 나누어 있으므로 VS Code의
Outline 또는 `region` 접기를 사용하시면 됩니다.

### Master와 같이 추가·수정된 공통 계약

- `inspection_interfaces/srv/OperatorCommand.srv`: 터미널/HMI의 운전 요청 진입점
- `inspection_interfaces/msg/SystemCommand.msg`: 전체 명령과 상·하층 개별 재가동을
  구분하는 `target_conveyor_id`
- `inspection_common/node_base.py`: 작업 노드의 targeted conveyor command 확장점과
  Master Ctrl+C 안전 종료 연결
- `inspection_control/control_node.py`: 실제 Mega/TB6600 개별 재가동을 붙일
  `handle_targeted_conveyor_command()` 확장점
- `tools/test_domain_contracts.py`: ROS 없이 FSM·FIFO·Sensor3 잠금·복구 guard를
  검사하는 회귀 테스트

## 3. 반드시 읽어야 하는 핵심

처음에는 아래 순서로만 읽으시면 충분합니다.

1. `system_fsm.py`
   - `SystemEvent`
   - `_TRANSITIONS`
   - `decide_system_transition()`
2. `product_flow.py`
   - `ProductContext`의 상태 변경 함수
   - `lock_at_sensor3()`
   - `ProductLedger.oldest_in_state()`
   - `remove_completed_prefix()`
3. `master_node.py` Block 1
   - `_handle_operator_command()`
   - `request_initialize()`, `request_run()`, `request_pause()`, `request_resume()`
   - `_apply_system_event()`
4. `master_node.py` Block 3~6의 정상 공정
   - `_handle_sensor_event()`
   - `_start_station_cycle()`
   - `_request_station_capture()`
   - `_handle_station_result()`
   - `_handle_sensor3_entry()`
   - `_schedule_actuation()`
   - `_handle_actuation_result()`
5. `master_node.py` Block 7
   - `_verify_resume_conditions()`
   - `_verify_reset_entry_conditions()`
   - `confirm_reset_completed()`
6. `master_node.py` Block 8
   - `_accept_locked()`
   - `_emit_log_event()`
   - `_begin_shutdown_sequence()`

## 4. 나중에 찾아봐도 되는 보조 함수

아래는 헌법처럼 반드시 기억할 내용이 아니라, 오류를 추적할 때 찾아보면
되는 함수입니다.

- Block 2의 Future callback 전체: Action/Service 비동기 응답 연결 코드
- `_fill_command_header()`: session·command ID·digest를 공통 입력
- `_publish_system_command()`: PAUSE/RESUME/RESET Topic 생성
- `_publish_spool_record()`: SQLite record를 `LogEvent`로 복원
- `_handle_log_persisted_ack()`: LogNode가 commit한 항목만 spool에서 제거
- `_check_operation_deadlines()`: Action·PAUSE·종료 timeout 분기
- `snapshot()`, `_touch()`: 로그용 상태 스냅샷과 revision 증가

## 5. 테스트 파일을 어디까지 읽을지

`ros2_ws/tools/test_domain_contracts.py`는 구현 코드가 아니라 규칙을 깨뜨리지
않았는지 확인하는 회귀 시험입니다. 처음에는 모두 정독하지 않으셔도 됩니다.

우선 볼 테스트:

- `test_system_fsm_normal_run_pause_and_resume`
- `test_station_aggregation_sensor3_and_fifo_reorder`
- `test_capture_failure_becomes_forced_ng_only_at_sensor3`
- `test_sensor_registry_rejects_duplicate_conflict_gap_and_out_of_order`
- `test_fifo_removes_only_contiguous_completed_prefix`
- `test_equipment_guards_require_explicit_physical_confirmation`

처음에 건너뛰어도 되는 부분:

- `make_rgb8_png()`와 Vision 이미지 artifact 테스트
- `CommonContractTests`의 digest·idempotency 세부 검증
- `LogContractTests`의 SQLite 구문
- `verify_skeleton.py`의 AST/XML 기계적 검사 코드

단, 코드를 수정한 후에는 읽지 않더라도 두 검증 명령은 모두 실행해야
합니다.

## 6. 아직 장비 때문에 확정하지 못한 TODO

`hardware.yaml`에서 빈 값·0으로 남겨 둔 항목은 부팅 실패를 뜻하는 값이 아니라
`장비 시험 전이므로 START 금지`를 뜻하는 fail-closed 표시입니다.

- Mega에 연결된 Sensor1/2/3 ID, pin, polarity
- 센서 debounce·rearm·stuck 시간과 step 기준
- Sensor1/2 감지 지점에서 Station A/B 촬영 지점까지의 step offset
- 오픈루프 위치 오차 허용치
- Station A 실제 카메라 3대와 Station B 1대의 serial/role ID
- GigE Action Command의 device key, group key, group mask
- 위치·촬영·액추에이터·PAUSE·종료 timeout
- FIFO soft/hard 한도와 Vision queue 크기의 실제 생산 값
- Master/Log SQLite 경로, 디스크 경고·일시정지 임계값
- 완료 ProductContext 10분 보존값이 실제 late result 분포에 충분한지
- E-stop 물리 회로와 Control→Master 상태 연결

`EquipmentState`는 이미 구현되어 연결되어 있습니다. Control이 상태가 바뀔
때만 발행하고, Master `_handle_equipment_state`가 `update_equipment_snapshot()`으로
안전 guard mirror를 갱신한 뒤 `confirm_all_conveyors_running()`,
`confirm_all_conveyors_stopped()`, `confirm_conveyor_resumed()`,
`confirm_reset_completed()`를 실제 상태 전이에 맞춰 호출합니다. 필드는
상·하층 실제 RUN/STOP, Sensor1/2/3 CLEAR, 액추에이터 안전 위치뿐이며,
작업 구역 CLEAR는 `line_clear_confirmed`와 의미가 중복돼 포함하지 않고,
E-stop은 보고할 센서가 없어 여전히 미해결입니다(위 목록 참고).

아직 확정되지 않은 계약은 `EquipmentCommandResult` 하나입니다: 원본
`command_id`와 대상 장비를 포함해 RUN/STOP/RESET/층별 재가동이 **왜**
실패했는지(Mega 오류 코드 등)를 알려주는 완료 event입니다. 지금은 상태
전이만으로 확인하기 때문에 최종적으로 원하는 상태에 도달했는지는
알 수 있지만, Control이 애초에 명령을 거부했는지 등 원인 진단은
불가능합니다. 이름은 아직 확정 인터페이스명이 아니라 역할을 설명하기
위한 임시 명칭입니다. Control 담당자와 payload를 합의한 다음 별도
브랜치에서 `inspection_interfaces`와 양쪽 노드를 함께 변경합니다.

Master가 RESET 또는 worker 재시작으로 `command_epoch`를 증가시키면 기존
GetNodeStatus 결과는 더 이상 READY 증거로 사용하지 않습니다. RESET은 worker를
`RECOVERING`으로 바꾸므로 세 worker 모두 InitializeNode부터 다시 진행합니다.
단일 worker 재시작 때는 해당 worker만 재초기화하고, 나머지는 Action 초기화
결과를 유지한 채 GetNodeStatus만 다시 조회합니다. heartbeat timeout이나
`DEGRADED` 감지 때도 해당 worker의 InitializeNode 재시도를 예약합니다.
따라서 worker 구현의 `initialize_node_resources()`는 프로세스당 한 번만 호출되는
함수가 아닙니다. RESET·통신 복구 후 다시 호출될 수 있으므로 자원 중복 생성,
카메라 이중 open, DB connection 누수를 만들지 않도록 멱등하게 작성해야 합니다.

`PositionProduct`의 Goal 수락 전 timeout은 물리 이동이 시작되지 않은 것으로
취급하여 `PAUSED` 복구 경로를 사용합니다. Goal 수락 후 Result·위치가 불명하면
`FAULT_STOP + LINE_CLEAR_REQUIRED`로 올립니다. FAULT_STOP 뒤 도착한 비동기
결과는 원장을 바꾸지 않고 진단 로그만 남깁니다. Vision 결과·실패는 판정,
점수, revision, 모델·실패 정보와 작업 식별자까지 보존합니다. 단, 반복되는
Capture feedback과 Vision queue state는 고빈도 telemetry이므로 FAULT_STOP 중
로그 없이 무시합니다. LINE_CLEAR 또는 제자리 RESET을 완료할 때는 이전 Vision
queue pause/recovery flag도 함께 지웁니다. 이미 종료된 cycle의 늦은
`PositionSettled`는 경고 후 무시합니다.

판정 상수의 `PASS`는 공정 용어 `OK`와 같은 의미입니다. 코드와 ROS message는
`PASS`를 사용하고 HMI 표시 문자열은 `OK`로 둘 수 있습니다.

hardware profile의 첫 RUN 전에는 Control이 위 실제 상태를 보고한 뒤
`OperatorCommand.CONFIRM_LINE_CLEAR`로 작업자 확인까지 들어와야 START guard가
열립니다. 해당 확인은 신규 RUN이 실제로 시작되면 소비됩니다.

## 7. 추천 학습 순서

1. 이 파일의 `전체 공정 읽기 지도`를 본다.
2. `product_flow.py`에서 제품 한 개가 어떻게 변하는지 본다.
3. `master_node.py` Block 3→4→5→6만 연속해서 본다.
4. 정상 흐름이 잡히면 Block 1·2의 초기화를 다시 본다.
5. 마지막에 Block 7·8의 오류 복구와 로그를 본다.

이 순서는 파일 순서가 아니라 `제품 한 개의 이야기`를 따라가는 순서입니다.
