# 코드 골격 완성을 위한 필수 결정사항

> **v2 상태 공지 (2026-08-16):** 이 문서는 질의 당시의 상세 체크리스트입니다. 이후 승인된 `GIGE_ACTION_COMMAND`, v2 공통 권장안, Queue/Log 정책은 같은 폴더의 `README.md`와 현재 코드에 반영되었습니다. 아래의 “결정 필요” 표시는 전부 현재 미결정을 뜻하지 않습니다. 구현자는 반드시 폴더 `README.md`의 최신 결정 묶음을 먼저 확인하십시오. 이 문서의 “Broadcast software trigger” 표현은 현재 계약에서 GigE Vision Action Command broadcast를 뜻합니다.

## 1. 문서 목적

이 문서는 ROS 2 Jazzy 기반 비전 검사 시스템의 **노드 간 통신, 공통 데이터 구조, 상태 객체, 비동기 Queue 및 mock 기반 실행 골격**을 구현하기 전에 확정해야 할 계약을 정리한다.

MasterNode, ControlNode, VisionNode, LogNode의 상세 장비 제어 알고리즘과 실제 비전 추론 알고리즘은 이 문서의 범위에서 제외한다. 단, 상세 구현체가 나중에 교체될 수 있도록 노드 경계와 추상 인터페이스는 여기서 확정한다.

### 상태 표기

- `확정`: 현재 대화에서 결정되었으며 그대로 코드 계약에 반영한다.
- `결정 필요`: 코드 골격 작성 전에 사용자가 값을 지정해야 한다.
- `장비 후 확정`: 골격에는 설정 키와 검증 로직을 만들되 실제 값은 장비 시험 후 지정한다.

## 2. 이미 확정된 상위 정책

- [x] LED는 외부 LED Controller로 상시 점등하며 ROS 2 및 Arduino 코드에서 밝기와 ON/OFF를 제어하지 않는다.
- [x] ControlNode는 카메라 trigger 및 LED 출력을 소유하지 않는다.
- [x] 카메라 촬영은 VisionNode가 HIKROBOT MVS SDK의 Broadcast software trigger를 호출하여 수행한다.
- [x] MasterNode는 ControlNode로부터 촬영 위치 도달·정지·안정화 완료를 받은 뒤 VisionNode에 `CaptureProduct` Action을 요청한다.
- [x] `CaptureProduct`는 필수 프레임 획득, 이미지 파일 저장, 파일 가독성 확인, 추론 Queue 등록까지 완료되어야 성공한다.
- [x] 추론 Queue에는 raw frame이나 이미지 byte 배열을 넣지 않는다.
- [x] 추론 Queue에는 `frame_batch_id`와 필수 이미지 파일 경로 목록을 포함한 `InferenceJob`을 넣는다.
- [x] Worker는 Queue에서 `InferenceJob`을 꺼내 이미지 파일 경로를 통해 입력 이미지를 읽고 병렬 추론한다.
- [x] 필수 카메라 중 하나라도 trigger·프레임·파일 저장·skew 검증에 실패하면 해당 Station의 필수 카메라 전체를 재촬영한다.
- [x] 재촬영은 동일 `capture_id`, 증가한 `attempt`, 새로운 `frame_batch_id`를 사용한다.
- [x] 추론 timeout은 `InferenceJob`이 Queue에 등록된 시점부터 성공·실패 결과가 확정되는 시점까지의 **총 경과시간**으로 정의한다.
- [x] 중복 촬영 및 결과 적용은 `product_id + station_id + capture_id`를 기준으로 검증한다.

> 중요: Queue가 파일 경로만 보유하므로 기존 설계의 “이미지 저장 실패 시 메모리 이미지로 추론 계속” 정책은 사용할 수 없다. 이미지 파일 저장 또는 저장 후 가독성 검증이 실패하면 해당 Capture attempt는 실패하며, 재시도 정책에 따라 Station 전체를 재촬영한다.

## 3. 촬영 명령 Flow와 통신 계약

### 3.1 확정 Flow

```text
ControlNode
  촬영 위치 도달·컨베이어 정지·settling 완료
        ↓ POSITION_SETTLED
MasterNode
  제품·Station·물리 상태 검증
        ↓ CaptureProduct Action Goal
VisionNode
  필수 카메라 예약·상태 확인·이전 frame buffer 정리
        ↓
  MVS SDK Broadcast software trigger
        ↓
  필수 프레임 수집·timestamp/skew 검증
        ↓
  attempt별 이미지 파일 원자적 저장·가독성 확인
        ↓
  frame_batch_id + image_refs로 InferenceJob 생성
        ↓
  bounded FIFO Queue 등록
        ↓ CaptureProduct Result(success)
MasterNode
  촬영 성공 반영
        ↓ Resume Conveyor Command
ControlNode
  컨베이어 재가동
```

### 3.2 제거되는 기존 인터페이스와 객체

- [x] `/inspection/control/trigger_capture` 제거
- [x] `TriggerCapture.srv` 제거
- [x] `CAPTURE_ARMED → Master → Control` trigger 중계 경로 제거
- [x] ControlNode의 trigger pulse 생성 로직 제거
- [x] `LightRuntime` 제거
- [x] 조명 ON/OFF·밝기 제어 Message·Service 제거
- [x] `control.trigger.pulse_width_us` 제거
- [x] `control.light.channels` 제거
- [x] `control.light.stabilization_ms` 제거
- [x] `trigger_command_id` 제거

### 3.3 Control → Master 촬영 위치 완료 이벤트

### 5.1 Trigger 호출 단위

### 5.2 Trigger 시각

CaptureAttempt에 다음 시각을 저장한다.

```text

```


## 6. Capture Skew 계약

### 6.1 계산식

```text
capture_skew_us
= max(필수 카메라의 비교 가능한 촬영시각)
- min(필수 카메라의 비교 가능한 촬영시각)
```

- [x] 모든 카메라 timestamp를 저장한다.
- [x] `capture_skew_us`를 계산한다.
- [x] `capture_skew_us`, 원본 timestamp, 계산 기준을 LogNode로 전달한다.
- [x] 허용시간 초과 시 Capture attempt 실패로 처리한다.
- [x] 실패 시 동일 `capture_id`로 Station 필수 카메라 전체를 재촬영한다.
- [x] 허용시간은 ROS 파라미터로 수동 조정할 수 있게 한다.

권장 설정:

```text
vision.capture_skew_limit_us
vision.capture_skew_source
```

`capture_skew_source` 후보:

```text
CAMERA_TIMESTAMP
HOST_FRAME_RECEIVED_TIME
```

### 6.2 확정: host monotonic frame-arrival skew

PTP 지원·lock 여부와 관계없이 skew 판정은
`HOST_FRAME_RECEIVED_TIME`의 monotonic clock만 사용한다. 카메라 timestamp는
진단 metadata로 보존하지만 서로 직접 비교하거나 합격 판정에 사용하지 않는다.
따라서 아래 항목은 판정 차단사항이 아니라 향후 진단 개선 항목이다.

- [ ] MVS SDK의 frame timestamp가 노출 시작·노출 종료·프레임 생성 중 무엇을 의미하는지
- [ ] timestamp 단위 또는 device tick frequency
- [ ] 카메라 재연결·재부팅 시 timestamp 초기화 여부
- [ ] timestamp wraparound 여부
- [ ] 여러 카메라가 동일한 clock 기준을 사용하는지
- [x] `HOST_FRAME_RECEIVED_TIME`을 유일한 skew 기준으로 사용
- [ ] `vision.capture_skew_limit_us` 실제 값

구현 정책:

- sim/hardware 모두 host `time.monotonic_ns()` frame-arrival을 사용한다.
- MVS Action1은 `scheduled=false` 즉시 실행이며 PTP clock에 의존하지 않는다.
- hardware profile에서는 위 항목이 확정되지 않으면 Capture skew 검증을 `INIT_BLOCKED` 또는 `CONFIG_UNRESOLVED`로 처리한다.

사용자/장비 확인 결과:

```text
camera timestamp 의미:
timestamp 단위/tick frequency:
카메라 간 clock 동기화 가능 여부:
skew source:
capture_skew_limit_us:
```

## 7. 프레임과 Capture 요청 연결 계약

### 7.1 필수 상관관계 키

각 프레임은 VisionNode 내부에서 다음 키와 연결한다.

```text
session_id
product_id
station_id
capture_id
attempt
frame_batch_id
camera_id
sdk_frame_number
```

### 7.2 필수 처리 순서

```text
1. CaptureAttempt 생성
2. 필수 카메라 lock 획득
3. 이전 SDK frame buffer 정리
4. 카메라별 baseline frame number 저장
5. expected frame_batch_id 등록
6. Broadcast software trigger 호출
7. 도착 프레임 검증·업무 ID 연결
8. 필수 카메라 Barrier 완료 확인
9. timestamp/skew 검증
10. 이미지 파일 저장·가독성 확인
11. InferenceJob Queue 등록
12. 카메라 lock 해제
```

### 7.3 결정 필요: 프레임 식별·늦은 프레임 정책

정확히 지정해야 할 사항:

- [ ] SDK frame number가 카메라별 단조 증가하는지
- [ ] frame buffer flush API 사용 가능 여부
- [ ] Broadcast 전 baseline frame number를 얻을 수 있는지
- [ ] 한 카메라가 동시에 두 CaptureAttempt에 참여하는 것을 금지할지
- [ ] 동일 Station의 Capture Action을 직렬화할지
- [ ] Station A/B가 서로 다른 카메라를 사용하면 두 Station Capture를 동시에 허용할지
- [ ] 늦은 이전 attempt 프레임을 즉시 폐기할지 진단용 파일로 보존할지
- [ ] 동일 카메라에서 한 trigger에 여러 프레임이 도착하면 첫 유효 프레임만 사용할지

권장안:

- 카메라 하나당 활성 CaptureAttempt는 최대 1개
- 동일 Station Capture는 직렬화
- 카메라 구성이 겹치지 않으면 Station A/B 동시 Capture 허용
- 늦은 프레임은 판정에 사용하지 않고 메타데이터 로그만 남김
- 한 trigger당 첫 번째 완전한 유효 프레임만 사용

사용자 결정:

```text
Station 동시 Capture 허용 범위:
늦은 프레임 보존 방식:
다중 프레임 선택 규칙:
SDK frame number/flush 지원 확인:
```

### 8.3 결정 필요: 파일 계약

다음 값을 정확히 지정해야 한다.

- [ ] 파일 형식: `png`, `bmp`, `tiff` 등
- [ ] bit depth 보존 여부
- [ ] 파일 경로가 `data_root` 기준 상대경로인지 절대경로인지
- [ ] 디렉터리 규칙
- [ ] 파일명 규칙
- [ ] 저장 완료를 atomic rename으로 보장할지
- [ ] Queue 등록 전에 파일을 다시 열어 가독성을 검사할지
- [ ] SHA-256 등 파일 digest를 필수로 계산할지
- [ ] attempt 1 실패 이미지도 보존할지
- [ ] Capture 성공 후 파일 삭제 가능 시점

권장안:

```text
형식: PNG
경로: data_root 기준 상대경로
디렉터리: images/{session_id}/{product_id}/{station_id}/{capture_id}/attempt_{n}/
```

- [x] Worker는 파일 경로로 이미지를 읽는다.
- [x] Queue dequeue 순서는 FIFO다.
- [x] 결과는 `product_id + station_id + capture_id`로 적용한다.

### 10.2 총 timeout 정의

```text
total_inference_elapsed
= 현재 monotonic time
- enqueued_at_steady_ns
```

```text
deadline_steady_ns
= enqueued_at_steady_ns
+ vision.inference_total_timeout_ms
```

- [x] Queue 대기시간과 실제 Worker 실행시간을 모두 timeout에 포함한다.
- [x] `deadline_steady_ns`를 초과하면 해당 Job은 정상 결과를 생성할 수 없다.
- [x] QUEUED 상태이면 Queue에서 제거하고 `INFERENCE_TIMEOUT`으로 확정한다.
- [x] RUNNING 상태이면 `cancel_requested/expired`로 표시한다.
- [x] 실행 중인 엔진을 즉시 중단할 수 없으면 완료 결과를 폐기하고 `LATE_IGNORED`로 기록한다.
- [x] timeout 결과는 MasterNode와 LogNode에 전달한다.

### 10.3 결정 필요: Worker 병렬성

정확히 지정해야 할 사항:

- [ ] `vision.inference_worker_count`
- [ ] Worker 구현을 thread, process, async task 중 무엇으로 할지
- [ ] GPU 한 장에서 동시 추론을 허용할지
- [ ] Worker별 모델 인스턴스를 따로 로드할지 공유할지
- [ ] dequeue 순서만 FIFO로 보장할지, 결과 완료 순서까지 FIFO로 보장할지

- [ ] 실행 중 timeout 작업을 엔진 수준에서 취소할 수 있는지

## 12. 공통 CommandHeader와 멱등 정책

### 12.1 권장 CommandHeader

```text
string session_id
uint64 command_epoch
string command_id
string payload_digest
builtin_interfaces/Time issued_at
```

의미:

- `session_id`: 현재 생산 운전 식별자
- `command_epoch`: RESET·복구 후 이전 명령을 무효화하는 명령 세대
- `command_id`: 동일 업무 명령의 멱등키
- `payload_digest`: 같은 ID로 다른 명령이 들어오는 것을 검출하는 hash
- `issued_at`: 로그·추적용 UTC/ROS clock 시각

### 12.2 결정 필요

- [ ] CommandHeader를 적용할 Service/Action 목록
- [ ] 새 session 생성 시점
- [ ] `command_epoch` 증가 시점
- [ ] `command_id` 생성 형식
- [ ] payload 정규화 및 digest 알고리즘
- [ ] 같은 command_id·같은 digest 재수신 시 기존 결과 보존시간
- [ ] 같은 command_id·다른 digest 수신 시 시스템 영향

권장안:

- 모든 물리 동작 Service/Action과 Capture Action에 적용
- 새 RUN session 시작 시 새 `session_id`
- RESET 완료·복구 후 기존 명령 무효화 시 epoch 증가
- digest는 canonical field order의 SHA-256
- 동일 ID·동일 digest는 재실행하지 않고 기존 결과 반환
- 동일 ID·다른 digest는 `COMMAND_CONFLICT`, 물리 결과 불명 시 `FAULT_STOP`

- [ ] snapshot 변경 이력을 `system_events`에 전부 남길지
- [ ] revision 시작값과 증가 조건
- [ ] 오래된 revision이 늦게 도착했을 때 처리


## 19. 배포와 파일시스템 계약

### 결정 필요

- [ ] 네 노드를 한 Ubuntu PC에서 실행할지
- [ ] VisionNode와 LogNode가 동일 `data_root`를 공유하는지
- [ ] 분산 PC라면 NAS/shared mount를 사용할지
- [ ] 상대경로 기준 root를 누가 생성·검증할지
- [ ] VisionNode에 이미지 디렉터리 쓰기 권한이 있는지
- [ ] LogNode가 이미지 파일 존재·digest를 재검증할지
- [ ] Worker가 파일을 읽는 동안 삭제·이동을 금지하는 방식

- 1차 골격은 단일 Ubuntu PC

- 삭제·이동은 Log 보존 정책에서만 수행


## 20. ROS 2 QoS와 Callback 동시성

### 결정 필요

다음 인터페이스별 QoS를 지정해야 한다.

- [ ] Heartbeat: Best Effort / Keep Last 1 유지 여부
- [ ] SensorEvent: Reliable depth
- [ ] StationResult: Reliable depth와 application retry
- [ ] LogEvent: Reliable depth와 local spool 병행
- [ ] 복구·상태 Topic: Reliable 또는 Transient Local 여부

권장안:

```text
Heartbeat: Best Effort, Keep Last 1
SensorEvent: Reliable, Keep Last configurable
StationResult: Reliable + 결과 보존·재전송
LogEvent: Reliable + local spool
최신 장치 상태: Reliable, Keep Last 1
이산 오류·완료 이벤트: Reliable + 업무 ID 멱등
```

동시성 관련 지정값:

- [ ] CaptureCoordinator를 Station별로 직렬화할지
- [ ] Inference Queue dispatcher 수
- [ ] Worker 수
- [ ] 초기화 Action을 노드당 한 번만 실행하도록 직렬화할지
- [ ] 공유 상태 lock 방식

사용자 결정:

```text
QoS 승인/수정:
Capture 동시성:
Queue dispatcher 수:
초기화 직렬화 여부:
공유 상태 동기화 방식:
```

## 21. 코드 골격 착수 전 최종 필수 응답 목록

다음 항목에 답하면 노드 간 통신과 구조체 중심의 1차 코드 골격을 구현할 수 있다.

1. `PositionSettled` 필드 승인 또는 수정안
2. Capture Goal의 `required_camera_ids` 소유·검증 방식
3. Capture Feedback/Result 필드 승인 또는 수정안
4. `capture_id`와 `frame_batch_id` 형식
5. timestamp 영구 저장 범위와 `captured_at_utc` 생성 기준
6. 카메라 timestamp 동기화 가능 여부 또는 현재 미정 유지 확인
7. skew source와 sim/hardware 미확정 처리 방식
8. Station 동시 Capture 허용 범위
9. 늦은 프레임과 한 trigger의 다중 프레임 처리 방식
10. 이미지 파일 형식·경로·atomic 저장·digest·삭제 정책
11. 최대 Capture attempt·재촬영 간격·최종 실패 정책
12. Worker 수와 실행 방식
13. 결과 완료 순서 FIFO 필요 여부
14. Queue 최대 길이와 Queue full 제품 정책
15. 총 추론 timeout 실제 값
16. 추론 재시도 횟수와 deadline 연장 여부
17. CameraResult 필드
18. CommandHeader 적용 대상·session·epoch·command ID·digest 규칙
19. Heartbeat와 노드 재시작 복구 정책
20. ErrorCode 숫자 체계
21. Status typed 필드와 JSON 경계
22. InitializeNode 재시도 ID·config digest·런타임 환경 필드
23. 카메라·Vision 복구 후 자동/수동 재개 정책
24. Log 영속화 ACK와 spool 방식
25. SQLite snapshot/revision/FK 도착 순서 정책
26. 배포 토폴로지와 공유 파일시스템
27. ROS 2 QoS와 callback/worker 동시성

수치가 아직 없는 항목은 ROS 파라미터 키와 validation 자리만 만들 수 있다. 그러나 **메시지 의미, 데이터 소유권, 실패 시 상태 전이, 멱등 처리 방식**은 골격 작성 전에 확정해야 한다.
